# 智能化提升度指标（intelligence-metrics）

> B22-⑤（第四轮诊断 F5）· 2026-11-03 · 状态：**口径定义层**（只定义不采集——
> 采集管道挂在既有 trace 事件上，等生产流量起来后 `harness.py trend` 扩展聚合即可）。
>
> 定位：回答总控指令「如何建立评估指标来衡量系统智能化与高效化的提升程度」。
> 原则：**每个指标 = 定义 + 数据源事件 + 口径公式** 三件套齐备才成立；
> 挂既有事件（不新增事件面），避免为指标另立数据源（双源必漂移——本包教训
> 已五次实证）。

## 一、四个一级指标

### M1 人工介入率（human_intervention_rate）

- **定义**：单个任务从接单到交付期间，系统停下等人工裁定（GATE）的次数。
  越低越智能——但**不得为降指标砍必要的人工门**（confirm_before_each_batch
  等门禁是安全设计，指标只度量、不驱动拆门）。
- **数据源事件**：`batch_open`（confirmed=false 的首次停等）+ `gate`
  （level=batch-close 且 exit≠0 的拒收再提交轮次）+ `member_return`
  （status=needs_decision 的回传）。
- **口径公式**：`M1 = GATE 停等总次数 / 任务数`。目标走势：随沉淀积累下降
  （同类决策应有先例可循，减少反复问）。

### M2 首过率（first_pass_rate）

- **定义**：一次通过闸4 交付门禁（P0=0 且无阻断）的任务占比。越高越可靠。
- **数据源事件**：`gate`（deck 非 `[loopA]` 前缀的生产事件，exit 码）。
- **口径公式**：`M2 = 首过任务数 / 总任务数`。与 M1 反向相关
  （M1 高可能换 M2 高——显式确认换取一次过）。

### M3 返工率（rework_rate）

- **定义**：触发 rework（成员产出被退回重做）的任务占比。越高说明任务包
  质量或成员产出越差——**直接检验 B21-① 任务包校验升维的效果**。
- **数据源事件**：`stage_exit`（stage 带rework 标记）/ Loop B state 的
  rework 动作记录。
- **口径公式**：`M3 = 含 rework 的任务数 / 总任务数`。B21 后预期下降
  （验收标准前置 ⇒ 成员产出与预期对齐度提高）。

### M4 自动化覆盖率（automation_coverage）

- **定义**：任务包 acceptance_criteria 中 judge_mode ∈ {机, 机+人} 的占比。
  度量「可机器判定的验收」覆盖面——越高系统越不依赖人工目检。
- **数据源事件**：任务包 JSON（assemble_spawn_prompt v5 结构化解析后的
  acceptance_criteria 数组）。
- **口径公式**：`M4 = 机判验收项数 / 总验收项数`。注意：这是**设计质量
  指标**不是结果指标——机判占比高但判据写错，反而更糟；读数须配合 M2。

## 三、红线

- **指标不得反噬门禁**：不得为美化 M1（少停等）而跳过 confirm 门；不得为
  美化 M2（高首过）而放宽 P0 判据。指标是仪表盘，不是油门。
- **无数据 ≠ 0**：任何指标在事件数不足时输出「无数据」而非默认 0（同 trend
  的 without_counts 纪律——把无数据当 0 是假的趋势）。
- **不另立第二事件源**：四指标全部挂既有事件；新增事件须先入
  `observability.trace_events` 双向对账（B19 断言守卫）。
