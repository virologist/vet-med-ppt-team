# 逐轮审阅 SOP（Loop B 旧课件内容优化）

> 建立：v3.8.0 增补 A（Loop A 第 2 批）
> 适用：**Loop B**——旧课件内容优化任务。**不适用于**新建 PPT（沿用五道闸既有确认流程）。
> 上位：`harness_requirements` 的管家节点确认门；`adjudication-rules.md` 迭代六原则（骨架冻结/方向裁决/增量门禁/检出≠判定/插入物避让/素材判读红线）在本 SOP 中全程生效。

## 0. 为什么立这条 SOP

v3.5.0–v3.7.0 来自一次**连续三轮**的课件迭代实战（97 页 / 100+ 条写入 / 14 张图逐张判读）。三轮的教训已抽象成六原则，但**"每轮停下来等用户读完再进下一轮"这个动作本身从未被机制化**——三轮都是一口气跑完的。立本 SOP 的目的：把"停等"从自觉变成契约。

## 1. 适用判定

| 情形 | 走本 SOP？ |
|---|---|
| 用户点名某份**已有** PPT 要求优化/深化/改稿 | ✅ 走 |
| 从零制作新 PPT | ❌ 不走，走 `sop-stages.md` 五道闸（两确认门） |
| 纯报告型复诊（只要诊断结论不制作） | ❌ 不走，走 WF-2 诊断入口即可 |
| 一次课件的多轮迭代（本 SOP 的目标场景） | ✅ 走，且**每轮都要停** |

## 2. 七种用户裁决语义（穷举，不得自造）

| 裁决 | 语义 | 状态机动作 |
|---|---|---|
| **接受** | 本轮全部条目通过 | 冻结本轮条目 → `round += 1` |
| **部分接受** | 只通过点名条目 | **只冻结被点名条目**；其余条目回退 `pending`，不消耗轮次配额 |
| **返修** | 条目方向对、执行不对 | **仍属当前轮**（`round` 不变）；生成返工单，回灌本轮 |
| **换方向** | 条目层面诊断对但切入点错 | 该条目作废 → 新条目入 `pending`，重新分档 |
| **暂停** | 用户要停，但不终止 | 状态 → `等待用户`，**保留全部现场**，可恢复 |
| **终止** | 用户明示不做 | 状态 → `用户取消`，冻结项与状态文件保留供后续恢复 |
| **沉默/超时** | — | **不构成确认**。状态维持 `等待用户`，绝不自动推进 |

> 硬约束：成员自评、AI 判断、"看起来没问题"均**不构成**用户确认。

## 3. 每轮必须展示的六项（缺任一项 = 本轮无效）

1. **本轮处理范围及问题**——条目 ID + 稳定页面 ID + 原文摘录 + 问题类型 + 严重度 + 判定方式（机/人）
2. **修改前后差异**——逐条对照。**禁止**"整体优化""已优化"这类无定位表述
3. **可阅读的修改后正文**——完整段落，不是摘要
4. **来源定位与边界**——PMID/DOI/指南条目 + 适用边界 + 未决项；无法核验的关键专业结论**不得进入正式内容**
5. **配图建议**——保留 / 替换 / 新增 + 页内位置 + 理由；图像类内容必须**先逐张判读图像本体**（迭代六原则·素材判读红线）：判读不出不得写、低清图降级"情境图"、来源缺失不编造、要素缺项显式挂账
6. **本轮验收结果 + 下一轮候选**——机器项引用**原始计数**（P0/P1/P2/P3），禁"归零/100%"表述（反自评失真红线）

## 4. 冻结粒度与批准失效

冻结对象是**条目级**，条目记录至少含：

```json
{
  "item_id": "R2-D3-007",
  "page_id": "s12",
  "file": "<工作副本>/content/s12_draft.md",
  "sha256": "<该文件内容哈希>",
  "round": 2,
  "user_decision": "accept|partial_accept",
  "decided_at": "<ISO8601>"
}
```

**失效规则（硬约束）**：内容文件 sha256 与冻结记录不一致 → 该条目的批准**自动失效**，必须重审。
禁止"改内容不重审"——这是本 SOP 最容易被绕过的漏洞。

## 5. 五类终止状态

| 状态 | 触发 | 允许动作 |
|---|---|---|
| 成功完成 | 全部条目冻结 + 制作交付 + 独立验收通过 | 交付 |
| 等待用户 | 待裁决 / 待审阅 / 待方向分档 | 停，等用户；**不得推进** |
| 能力或证据阻塞 | 关键能力缺失或关键结论无法核验 | 报缺口 + 核验方法；**不得降级冒充** |
| 达到预算但未完成 | 轮次/检索/无进展阈值触顶 | **暂停并报告，禁止宣布通过** |
| 用户取消 | 用户明示终止 | 停；保留状态文件供恢复 |

参数（`config/harness.yaml#loop_b`，均可调）：
`max_rounds` 轮次上限 · `retrieval_budget_per_round` 每轮检索预算 · `no_progress_threshold` 无进展轮次阈值 · `max_rework_per_item` 单条目返修上限。

## 6. 制作前置门（任一不满足即停）

- 已冻结条目**覆盖**制作输入的全部页面与素材
- 每条冻结项的 `file` sha256 与当前文件一致（不一致 → 批准失效，须重审）
- 内容、页面顺序、配图方案、模板**均已确认**

制作期遇内容问题 → **退回对应内容轮**，不得擅自改写已批准内容。

## 7. 断线恢复

读状态文件最小集：`task_id / source_ppt{sha256,mtime} / wip_dir / current_round / frozen_items[] / pending_items / budgets / blockers`。

禁止：重跑已确认条目、重新生成已冻结内容、覆盖 `_draft`。
恢复后先报"恢复到第 R 轮，已冻结 N 条，待办 M 条"，**等用户确认再继续**。

## 8. 状态文件位置（Loop B 专用）

`<工作区>/.workbuddy/loopB_state.json` —— 与 `task_state.json` **并存，不覆盖**（后者是五道闸的既有状态机，本 SOP 不改其语义）。
写入采用**单写者**（主理人）——成员不得直接写该文件，回传由主理人汇编后落盘。

## 9. 与既有规则的优先级

冲突时以本 SOP 为准的两条：
1. 本 SOP 的**逐轮停等**优先于任何"提高效率"的建议——效率不构成跳过的理由。
2. 迭代六原则**全文适用**（本 SOP 不重定义它们，只规定其在逐轮场景下的执行时点）。
