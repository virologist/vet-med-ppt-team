# 逐轮审阅 SOP（Loop B 旧课件内容优化）

> 建立：v3.8.0 增补 A（Loop A 第 2 批）
> 适用：**Loop B**——旧课件内容优化任务。**不适用于**新建 PPT（沿用五道闸既有确认流程）。
> 上位：`harness_requirements` 的管家节点确认门；`adjudication-rules.md` 迭代六原则（骨架冻结/方向裁决/增量门禁/检出≠判定/插入物避让/素材判读红线）在本 SOP 中全程生效。

## 0. 为什么立这条 SOP

v3.5.0–v3.7.0 来自一次**连续三轮**的课件迭代实战（97 页 / 100+ 条写入 / 14 张图逐张判读）。三轮的教训已抽象成六原则，但**"每轮停下来等用户读完再进下一轮"这个动作本身从未被机制化**——三轮都是一口气跑完的。立本 SOP 的目的：把"停等"从自觉变成契约。

## 1. 适用判定

| 情形 | 走本 SOP？ |
|---|---|
| 用户点名某份**已有** PPT 要求优化/深化/改稿 | ✅ 走 |
| 从零制作新 PPT | ❌ 不走，走 `sop-stages.md` 五道闸（两确认门） |
| 纯报告型复诊（只要诊断结论不制作） | ❌ 不走本 SOP（逐轮停等不适用），走**纯诊断任务出口**（见 §13）：产出 `references/diagnosis-report-schema.yaml` 定义的**诊断报告**。**「只诊断不修改」是一条合法的任务终态**（交付物 = 诊断报告，**不含 PPTX**） |
| 一次课件的多轮迭代（本 SOP 的目标场景） | ✅ 走，且**每轮都要停** |

## 2. 转换层与前置检查（Loop B 第 1 步，v3.8.0 增补 N1/N2）

> 在任何诊断动作之前完成。**原 PPTX 只读**，所有产出落在工作副本。

### 2.1 双源转换（三份产出，互不覆盖）

| 产出 | 工具 | 落点 | 性质 |
|---|---|---|---|
| 原始 Markdown | `markitdown <原PPT>` | `<wip>/_raw/original.md` | **只读留存**，任何改写不得覆盖 |
| 改写稿 | 人工/成员撰写 | `<wip>/content/<page_id>_draft.md` | 迭代对象 |
| 资产目录 | `python3 scripts/extract_assets.py <副本> --out-dir <wip>/_assets` | `<wip>/_assets/` + `manifest.json` | 图片/表格/OLE 清单 |

**双源核验硬约束**：备注覆盖必须**同时**看 markitdown 文本层与 manifest 的源课件备注字段——v3.2.0 实测 4 份样本中 **2/4 口径不一致**（如"全链攻防术"deck 报 0% 但 markitdown 拿到 29 个 Notes 块）。任一来源不得单独作为"备注已覆盖"的依据。

**图片引用修复（v3.8.2 起有脚本，不再靠手工）**：

```bash
python3 <包>/scripts/fix_md_image_refs.py \
  --md <wip>/_raw/original.md \
  --manifest <wip>/_assets/manifest.json \
  --out <wip>/_raw/original.refs.md \
  --deck <原PPTX路径>          # 可选：三方计数核验（deck 图形数 / md 引用数 / manifest 资产数）
```

- 配对依据（**2026-10-22 实测**，markitdown 0.1.7 对 PPTX 输出 `<!-- Slide number: N -->` + `![原文件名](PictureN.jpg)`，target 指向不存在的文件）：**页号 + 页内序号**；若 md 的 target 在磁盘真实存在则升级为 **sha256 比对**证据
- 无法对应的图**显式列为"引用缺失"**（报告 `missing_refs` + 行内 `REF-MISSING` 标记，原文本保留），**不得留空链接或用占位图**；manifest 有而 md 未引用 → 记 `orphan_assets`（可能 markitdown 漏出图，需对照渲染图确认）
- 退出码：`0` 全解析且三方一致 / `1` 存在未决项（缺失/孤立/计数不一致，**须人工处置，不得当作通过**）/ `2` 用法错误（`--out` 与 `--md` 相同）/ `3` 文件缺失 / `4` 运行错误
- 原始 `original.md` **只读留存**，修复稿另存 `original.refs.md`（脚本对 `--out == --md` 直接 exit 2）

### 2.2 渲染前置（视觉诊断不可绕过）

```bash
/opt/homebrew/bin/soffice --headless --convert-to pdf --outdir <wip>/_render <副本>.pptx
pdftoppm -png -r 120 <wip>/_render/<name>.pdf <wip>/_render/page   # 或 sips 转单页
```

- **视觉类诊断（版式/重叠/清晰度/图文匹配）必须基于渲染图**，不得仅凭 Markdown 判断
- 渲染能力不可用时，相关结论**必须显式标注"未经渲染核实"**，并说明缺哪一步
- 渲染失败按 §5「能力或证据阻塞」上报，不得降级为"看着没问题"

## 3. 诊断与批次上限（v3.8.0 增补 N3）

### 3.1 条目字段规范

每条诊断条目必须携带以下字段，缺任一项视为条目不合格：

| 字段 | 说明 |
|---|---|
| `item_id` | 稳定标识（如 `R2-D3-007`），跨轮次不重号 |
| `page_id` | 稳定页面 ID（如 `s12`），**不随改写变化** |
| `原文摘录` | 该页当前实际文字，供用户对照 |
| `关联素材` | 对应 `_assets/` 下的具体文件（无图则写"无"） |
| `诊断维度` | 内容准确性 / 知识更新 / 教学逻辑 / 结构层次 / 图文匹配（Loop B 五维轻量口径） |
| `严重度` | P0 硬阻断 / P1 交付前清零 / P2 建议 |
| `判定方式` | \[机\] 机器可判 / \[人\] 需人判 |
| `责任人` | dvm（内容/知识更新）/ pedagogy（教学逻辑/结构）/ visual（图文匹配/视觉） |

> 五维口径与七维量规的关系：七维量规是**诊断入口**标准（新建 PPT 的 WF-2 与纯诊断任务共用）；Loop B 逐轮优化用上表五维轻量口径。两者并存，**是两条轴**，靠条目的可选字段「七维检查项」关联。
> **v3.17.0 变更**：七维量规的**唯一执行源已内化进本包** —— `references/seven-dimension-rubric.md`
> （内化自 `teaching-ppt-studio` v2.6.0 的 `references/seven-dimension-rubric.md`，2026-10-17 版 148 行，
> 已做**去领域化**改造；上游更新时需重新比对）。
> 此前本文件写「量规唯一源仍在 `teaching-ppt-studio`，本团不复制其全文」——**该口径已于 v3.17.0 作废**：
> 不复制 → 换机器 / 换用户时该诊断入口**静默失效且无任何提示**（`plugin.json` 无依赖声明字段，
> 平台亦无此字段可声明，详见 `references/dependency-manifest.yaml#platform_fact`）。
>
> **v3.17.0 补充**：上表八字段是**必填最小集**；其**机器可校验形态**（字段名、必填集、枚举取值、
> 落盘路径、终止态产物清单）的唯一源为 `references/diagnosis-report-schema.yaml`——本表与该 schema
> **逐字段一致**（schema 另列的补充字段一律可选，不替代、不改名、不改语义）。
> 「判定方式」取值以 schema 为准：**`机` / `人` / `机+人`**（本表写的 `[机]/[人]` 是其**子集**；
> 「机+人」= 脚本初筛 + 人工复核，检出≠判定）。

### 3.2 全局扫描 vs 每轮小批

- **全局扫描**：一次跑完所有页面，产出完整条目清单（不逐条执行）——只在第 1 轮做一次
- **每轮小批**：每轮只处理 `loop_b.budgets.max_items_per_round` 条（默认 **5**，可确认调整）
- 小批目的是**让用户能真正读完**——超过此量应主动分轮，不得为"效率"一次塞满

### 3.3 制作后三项检查（v3.8.0 增补 N4）

制作完成后（不只是前置门），verifier 必须逐项检查并如实报告：

| 检查 | 方法 | 当前实现状态 |
|---|---|---|
| 打开 | 用 python-pptx 打开成品无异常 | 可用（python-pptx 1.0.2 实测） |
| 渲染 | `soffice --convert-to pdf` 成功且页数符合预期 | 可用（LibreOffice 26.8.1.1 实测） |
| 对象可编辑性 | 逐类枚举：文本框 / 原生表格 / 原生图表 / 组合形状 | 部分——**GEO-003 已实现**（v3.8.2，见下）；**API-001 保持人工项**（写入时行为，文件态不可检，见下） |

**可编辑性分级判据**：文本/表格/流程图/常规数据图 = 须为原生对象；照片 = 可为图片但须标注独立；**整页截图或 SVG 冒充原生页面/数据图 = 直接判不合格**。

**GEO-003 / API-001 的实现状态（v3.8.2 更新，如实标注）**：

| 码 | 状态 | 说明 |
|---|---|---|
| **GEO-003** 插入物与既有形状空间冲突 | ✅ **已实现**（`ooxml_lint.py` GeoChecker，WARN 级）；**v3.10.0 起须配 `--geo-baseline`** | 逐页取 `a:xfrm` 的 off/ext 求矩形（GROUP 按 chOff/chExt 换算，规避 GEO-002 误报），两两求交，重叠面积/较小者 ≥ `--geo-threshold`（默认 15%）即报出形状名与重叠率。**只报 WARN 不报 ERROR**：教学课件存在有意叠放（文字压图），机器分不清设计与事故，判 ERROR 会一律阻断合法设计。**基线豁免**：实测默认模板 33 页自身就产生 552 条 GEO-003（模板固有底纹叠放），不加 `--geo-baseline` 会淹没新增遮挡、使 V7 无法判定；加基线后同页序号+同名形状对+重叠率差 ≤5% 判 `inherited` 不计 WARN，`geo_new_overlap`（新增）才是判据 |
| **API-001** 写入属性名凭记忆猜测 | ⚠️ **保持人工项（不实现）** | 这是**写入时行为**而非文件态缺陷——任何 lint 都无法从成品文件反推"当初是不是猜的属性名"。防线仍在写入纪律：批量写入原子语义 + 首次使用的属性名先查能力参考 + 报错列出的合法属性名直接采纳（见 ppt-producer MD） |
| GEO-001 图片单维尺寸失控 | ⚠️ 人工项 | 属版式/设计判断，需看渲染图，非坐标可判 |
| GEO-002 GROUP 越界误报 | ✅ 已规避 | 已在 GeoChecker 的 GROUP 坐标换算中处理 |

## 4. 七种用户裁决语义（穷举，不得自造）

| 裁决 | 语义 | 状态机动作 |
|---|---|---|
| **接受** | 本轮全部条目通过 | 冻结本轮条目 → `round += 1` |
| **部分接受** | 只通过点名条目 | **只冻结被点名条目**；其余条目回退 `pending`，不消耗轮次配额 |
| **返修** | 条目方向对、执行不对 | **仍属当前轮**（`round` 不变）；生成返工单，回灌本轮 |
| **换方向** | 条目层面诊断对但切入点错 | 该条目作废 → 新条目入 `pending`，重新分档 |
| **暂停** | 用户要停，但不终止 | 状态 → `等待用户`，**保留全部现场**，可恢复 |
| **终止** | 用户明示不做 | 状态 → `用户取消`，冻结项与状态文件保留供后续恢复 |
| **沉默/超时** | — | **不构成确认**。状态维持 `等待用户`，绝不自动推进 |

> 硬约束：成员自评、AI 判断、"看起来没问题"均**不构成**用户确认。

## 5. 每轮必须展示的六项（缺任一项 = 本轮无效）

1. **本轮处理范围及问题**——条目 ID + 稳定页面 ID + 原文摘录 + 问题类型 + 严重度 + 判定方式（机/人）
2. **修改前后差异**——逐条对照。**禁止**"整体优化""已优化"这类无定位表述
3. **可阅读的修改后正文**——完整段落，不是摘要
4. **来源定位与边界**——PMID/DOI/指南条目 + 适用边界 + 未决项；无法核验的关键专业结论**不得进入正式内容**
5. **配图建议**——保留 / 替换 / 新增 + 页内位置 + 理由；图像类内容必须**先逐张判读图像本体**（迭代六原则·素材判读红线）：判读不出不得写、低清图降级"情境图"、来源缺失不编造、要素缺项显式挂账
6. **本轮验收结果 + 下一轮候选**——机器项引用**原始计数**（P0/P1/P2/P3），禁"归零/100%"表述（反自评失真红线）

## 6. 冻结粒度与批准失效

冻结对象是**条目级**，条目记录至少含：

```json
{
  "item_id": "R2-D3-007",
  "page_id": "s12",
  "file": "<工作副本>/content/s12_draft.md",
  "sha256": "<该文件内容哈希>",
  "round": 2,
  "user_decision": "accept|partial_accept",
  "decided_at": "<ISO8601>"
}
```

**失效规则（硬约束）**：内容文件 sha256 与冻结记录不一致 → 该条目的批准**自动失效**，必须重审。
禁止"改内容不重审"——这是本 SOP 最容易被绕过的漏洞。

## 7. 五类终止状态

| 状态 | 触发 | 允许动作 |
|---|---|---|
| 成功完成 | 全部条目冻结 + 制作交付 + 独立验收通过 | 交付 |
| 等待用户 | 待裁决 / 待审阅 / 待方向分档 | 停，等用户；**不得推进** |
| 能力或证据阻塞 | 关键能力缺失或关键结论无法核验 | 报缺口 + 核验方法；**不得降级冒充** |
| 达到预算但未完成 | 轮次/检索/无进展阈值触顶 | **暂停并报告，禁止宣布通过** |
| 用户取消 | 用户明示终止 | 停；保留状态文件供恢复 |

> **v3.17.0 补充：另有一个「任务级」终态**——**「诊断完成（只诊断不修改）」**。
> 它**不属于**上表五类：上表五类是**进入逐轮优化之后**的 Loop B 状态机终止态
> （`loop terminate --reason <五类>` 对自造状态 exit 2，**本 SOP 不改这条约束**）。
> 「只诊断不修改」是**任务类型**——它在**接单阶段就分流**，根本不进入逐轮停等流程，
> 其交付物是诊断报告（见 §13 与 `references/diagnosis-report-schema.yaml#termination`）。
> **不得**把它硬塞进五类之一（那会让状态机拒绝一个合法终态）；
> **也不得**因为「五类穷举」就否认它是合法终态——两者是**不同层级**，不是同一张表。

参数（`config/harness.yaml#loop_b`，均可调）：
`max_rounds` 轮次上限 · `retrieval_budget_per_round` 每轮检索预算 · `no_progress_threshold` 无进展轮次阈值 · `max_rework_per_item` 单条目返修上限。

## 8. 制作前置门（任一不满足即停）

- 已冻结条目**覆盖**制作输入的全部页面与素材
- 每条冻结项的 `file` sha256 与当前文件一致（不一致 → 批准失效，须重审）
- 内容、页面顺序、配图方案、模板**均已确认**

制作期遇内容问题 → **退回对应内容轮**，不得擅自改写已批准内容。

## 9. 断线恢复

读状态文件最小集：`task_id / source_ppt{sha256,mtime} / wip_dir / current_round / frozen_items[] / pending_items / budgets / blockers`。

禁止：重跑已确认条目、重新生成已冻结内容、覆盖 `_draft`。
恢复后先报"恢复到第 R 轮，已冻结 N 条，待办 M 条"，**等用户确认再继续**。

## 10. 状态文件位置（Loop B 专用）

`<工作区>/.workbuddy/loopB_state.json` —— 与 `task_state.json` **并存，不覆盖**（后者是五道闸的既有状态机，本 SOP 不改其语义）。
写入采用**单写者**（主理人）——成员不得直接写该文件，回传由主理人汇编后落盘。

**v3.9.0 起由 `scripts/harness.py loop` 读写该文件**（主理人是唯一调用者，契合单写者约定）：

| 本 SOP 条款 | 对应命令 | 机器背书 |
|---|---|---|
| 启动/原件指纹存档 | `loop start --deck <原PPTX>` | sha256+size+mtime 存档，`status/verify` 可复检 |
| §1 九项接单 | `loop intake --file <九项.json>` | A 类 5 项缺一即 `confirmed=false` + exit 1 |
| §3.1 条目八字段 | `loop add-item --item --page --file` | item_id/page_id/file/sha256 落盘 |
| §4 七种裁决 | `loop continue --decision \| loop freeze --decision` | 缺 `--decision` 即 exit 2（沉默不推进） |
| §4 部分接受 | `loop freeze --items I-001,I-002 --decision partial_accept` | 只冻点名条目，`round` 不变 |
| §4 返修 | `loop rework --item I-001` | 不进位；超上限挂阻塞 |
| §6 冻结失效 | `loop verify` | sha256 漂移 → `invalidated` + exit 1 |
| §7 五类终止 | `loop terminate --reason <五类>` | 自造状态 exit 2；预算触顶自动置「达到预算但未完成」 |
| §8 制作前置门 | `loop make-gate` | 四项全过才 exit 0 |
| §9 断线恢复 | `loop resume` | 只报不推进，置等待确认 |

回归：`python3 scripts/test_loop_state.py`（33 例）。

### 10.1 通道纪律（v3.8.0 增补 N6）

- **只有主理人可向用户提问与接收确认**；成员遇到缺失信息时把问题写进 `issues`，由主理人转达，**不得直接联系用户**
- 成员之间**禁止横向直连**，跨成员信息流一律经主理人中转
- 成员**不得代写**其他成员的专业结论；主理人只做汇编与裁决
- 沉默不等于批准；用户未回应时状态停在 `等待用户`，**不自动推进**

## 11. 终审验收清单（v3.8.0 增补 N5）

交付前逐项打勾（v3.10.0 扩为 11 项），**每项须给出判定依据**，无法检查的写明原因——**不得因"看起来没问题"写通过**：

| # | 验收项 | 判定方式 | 未通过处置 |
|---|---|---|---|
| 1 | 原件未改动 | 原件 sha256/mtime 与任务开始时比对 | 立即停止并上报 |
| 2 | 新建 PPT 能力未回归 | 跑 `ensure_settings` + `test_five_gates.py` | 阻断交付 |
| 3 | 素材链接可解析且可回溯原页 | 逐条解析 `_draft.md` 图片引用 + 反查 `page_id` | 标注缺失项 |
| 4 | 关键专业结论有可核对来源 | `harness.py verify-ref --path <cases_library.json> --online` | 降级或退回内容轮 |
| 5 | 每轮用户批准可追溯 | `loopB_state.frozen_items[]` 含 item_id/file/sha256/decided_at | 不得进入制作 |
| 6 | 配图决策与最终页面一致 | 配图清单 vs 新版页逐条核 | 返修 |
| 7 | PPT 内容与批准稿一致 | 成品文本层 diff `_draft` | 阻断交付 |
| 8 | 模板继承 + 打开 + 渲染 | 打开无异常 + 渲染页数符合 | 报缺口 |
| 9 | 对象可编辑性分级 | §3.3 四类判定 | 截图/SVG 冒充 = 不合格 |
| 10 | **无文字溢出或遮挡**（验收 V7） | `ooxml_lint.py <新版> --geo-baseline <模板>`：`geo_new_overlap == 0`；`geo_inherited` 如实记录豁免条数 | 新增重叠 >0 即返修；未跑基线豁免不得判通过 |
| 11 | 未实现/未测试的检查已标注 | 逐项标 [机]/[人]/lint 未实现 | 不报通过 |

## 12. 与既有规则的优先级

冲突时以本 SOP 为准的两条：
1. 本 SOP 的**逐轮停等**优先于任何"提高效率"的建议——效率不构成跳过的理由。
2. 迭代六原则**全文适用**（本 SOP 不重定义它们，只规定其在逐轮场景下的执行时点）。

## 13. 纯诊断任务出口（只诊断不修改 · v3.17.0 新增）

> 目的：把「只要诊断结论、不制作」从**没有出口的诉求**变成**有产物、有终态、有判据的合法任务**。
> 此前本文件 §1 写「纯报告型复诊 → 走 WF-2 诊断入口即可」，而 WF-2 的终点是**交付 PPT**——
> 那条路指向一个**不存在的出口**（诊断报告既无 schema、也不在交付清单里）。

### 13.1 判定与分流

| 判据 | 结论 |
|---|---|
| 用户明确说「只诊断 / 先别改 / 只要报告」 | ✅ 走纯诊断任务出口 |
| 用户要诊断**且**要改 | ✅ 走本 SOP 逐轮优化（诊断阶段用同一份七维量规，诊断报告作为增量门禁基线） |
| 判不出 | 必须追问「先给诊断报告，还是诊断完直接改？」——**不猜** |

分流发生在**接单阶段**，**不进入逐轮停等流程**；纯诊断任务**不消耗** Loop B 轮次配额。

### 13.2 产物（交付物清单）

结构（字段 / 必填集 / 枚举 / 落盘路径 / 终止态产物清单）唯一源 =
`references/diagnosis-report-schema.yaml`；此处只列清单：

| # | 产物 | 落点 |
|---|---|---|
| 1 | 诊断报告（机器态 YAML） | `<课件名>_wip/_diagnosis/<deck_id>_diagnosis_<YYYYMMDD-HHMM>.yaml` |
| 2 | 诊断报告（人读渲染版 MD） | 同目录同名 `.md`，章节顺序 = schema 的 `report` 段顺序（基线 → 扫描矩阵 → 条目 → 修复汇总 → 待裁决） |
| 3 | 诊断产物台账 | `<课件名>_wip/_diagnosis/_index.yaml`（deck_id / 报告路径 / sha256 / 生成时间，**自持**） |
| 4 | 渲染图证据 | `<课件名>_wip/_render/`（视觉类结论的证据；渲染不可用时报告须标「未经渲染核实」） |

**纯诊断任务不产出**：修改后的 PPTX、逐页修改说明、验收自检清单
（后二者属**制作阶段**的交付三件套，见 `references/delivery-spec.md`）。

### 13.3 终态与退出条件

终态 = **「诊断完成（只诊断不修改）」**（`task_level`，详见 schema 的 `termination` 段）。退出条件：

1. 七维扫描矩阵**全维逐项**齐备（未命中写 `hit: false`，不得只写命中项）
2. 每条问题条目**八字段齐全**（§3.1）
3. 修复级汇总的条目数与条目清单实际条数一致
4. 待裁决项的 `user_decision` **留空**（不得预填；沉默不构成确认）
5. 基线锚点齐全（物理页 / 隐藏页 / 可见页 + 门禁原始计数 + 原件指纹）

### 13.4 禁则

- ❌ 以「看起来没问题」代替未检查项（未检查须显式标注）
- ❌ 把「检测到」直接写成「判定成立」（检出≠判定）
- ❌ 纯诊断任务中产出 / 改写 PPTX 后仍声称本任务为「只诊断」终态
- ❌ 借用「五类终止状态穷举」否认本节终态（层级不同，见 §7 补充说明）
- ❌ 在诊断报告里把「建议修复级」写成「已执行」——路由是**建议**，裁决权在用户
