# 逐轮审阅 SOP（Loop B 旧课件内容优化）

> 建立：v3.8.0 增补 A（Loop A 第 2 批）
> 适用：**Loop B**——旧课件内容优化任务。**不适用于**新建 PPT（沿用五道闸既有确认流程）。
> 上位：`harness_requirements` 的管家节点确认门；`adjudication-rules.md` 迭代六原则（骨架冻结/方向裁决/增量门禁/检出≠判定/插入物避让/素材判读红线）在本 SOP 中全程生效。

## 0. 为什么立这条 SOP

v3.5.0–v3.7.0 来自一次**连续三轮**的课件迭代实战（97 页 / 100+ 条写入 / 14 张图逐张判读）。三轮的教训已抽象成六原则，但**"每轮停下来等用户读完再进下一轮"这个动作本身从未被机制化**——三轮都是一口气跑完的。立本 SOP 的目的：把"停等"从自觉变成契约。

## 1. 适用判定

| 情形 | 走本 SOP？ |
|---|---|
| 用户点名某份**已有** PPT 要求优化/深化/改稿 | ✅ 走 |
| 从零制作新 PPT | ❌ 不走，走 `sop-stages.md` 五道闸（两确认门） |
| 纯报告型复诊（只要诊断结论不制作） | ❌ 不走，走 WF-2 诊断入口即可 |
| 一次课件的多轮迭代（本 SOP 的目标场景） | ✅ 走，且**每轮都要停** |

## 2. 转换层与前置检查（Loop B 第 1 步，v3.8.0 增补 N1/N2）

> 在任何诊断动作之前完成。**原 PPTX 只读**，所有产出落在工作副本。

### 2.1 双源转换（三份产出，互不覆盖）

| 产出 | 工具 | 落点 | 性质 |
|---|---|---|---|
| 原始 Markdown | `markitdown <原PPT>` | `<wip>/_raw/original.md` | **只读留存**，任何改写不得覆盖 |
| 改写稿 | 人工/成员撰写 | `<wip>/content/<page_id>_draft.md` | 迭代对象 |
| 资产目录 | `python3 scripts/extract_assets.py <副本> --out-dir <wip>/_assets` | `<wip>/_assets/` + `manifest.json` | 图片/表格/OLE 清单 |

**双源核验硬约束**：备注覆盖必须**同时**看 markitdown 文本层与 manifest 的源课件备注字段——v3.2.0 实测 4 份样本中 **2/4 口径不一致**（如"全链攻防术"deck 报 0% 但 markitdown 拿到 29 个 Notes 块）。任一来源不得单独作为"备注已覆盖"的依据。

**图片引用修复**：markitdown 输出的图片链接需重写为 `<wip>/_assets/` 下的实际路径；无法对应的图**显式列为"引用缺失"**，不得留空链接或用占位图。

### 2.2 渲染前置（视觉诊断不可绕过）

```bash
/opt/homebrew/bin/soffice --headless --convert-to pdf --outdir <wip>/_render <副本>.pptx
pdftoppm -png -r 120 <wip>/_render/<name>.pdf <wip>/_render/page   # 或 sips 转单页
```

- **视觉类诊断（版式/重叠/清晰度/图文匹配）必须基于渲染图**，不得仅凭 Markdown 判断
- 渲染能力不可用时，相关结论**必须显式标注"未经渲染核实"**，并说明缺哪一步
- 渲染失败按 §5「能力或证据阻塞」上报，不得降级为"看着没问题"

## 3. 诊断与批次上限（v3.8.0 增补 N3）

### 3.1 条目字段规范

每条诊断条目必须携带以下字段，缺任一项视为条目不合格：

| 字段 | 说明 |
|---|---|
| `item_id` | 稳定标识（如 `R2-D3-007`），跨轮次不重号 |
| `page_id` | 稳定页面 ID（如 `s12`），**不随改写变化** |
| `原文摘录` | 该页当前实际文字，供用户对照 |
| `关联素材` | 对应 `_assets/` 下的具体文件（无图则写"无"） |
| `诊断维度` | 内容准确性 / 知识更新 / 教学逻辑 / 结构层次 / 图文匹配（Loop B 五维轻量口径） |
| `严重度` | P0 硬阻断 / P1 交付前清零 / P2 建议 |
| `判定方式` | \[机\] 机器可判 / \[人\] 需人判 |
| `责任人` | dvm（内容/知识更新）/ pedagogy（教学逻辑/结构）/ visual（图文匹配/视觉） |

> 五维口径与下游 skill 七维量规的关系：七维量规是**新建 PPT 的 WF-2 诊断入口**标准；Loop B 逐轮优化用上表五维轻量口径。两者并存，量规唯一源仍在 `teaching-ppt-studio`，本团不复制其全文。

### 3.2 全局扫描 vs 每轮小批

- **全局扫描**：一次跑完所有页面，产出完整条目清单（不逐条执行）——只在第 1 轮做一次
- **每轮小批**：每轮只处理 `loop_b.budgets.max_items_per_round` 条（默认 **5**，可确认调整）
- 小批目的是**让用户能真正读完**——超过此量应主动分轮，不得为"效率"一次塞满

### 3.3 制作后三项检查（v3.8.0 增补 N4）

制作完成后（不只是前置门），verifier 必须逐项检查并如实报告：

| 检查 | 方法 | 当前实现状态 |
|---|---|---|
| 打开 | 用 python-pptx 打开成品无异常 | 可用（python-pptx 1.0.2 实测） |
| 渲染 | `soffice --convert-to pdf` 成功且页数符合预期 | 可用（LibreOffice 26.8.1.1 实测） |
| 对象可编辑性 | 逐类枚举：文本框 / 原生表格 / 原生图表 / 组合形状 | 部分——`ooxml_lint` 对 GEO-003/API-001 等 **仅登记未实现**（见 CHANGELOG v3.5.0/v3.6.0），此类判定靠人工抽检并**显式标注"lint 未实现"** |

**可编辑性分级判据**：文本/表格/流程图/常规数据图 = 须为原生对象；照片 = 可为图片但须标注独立；**整页截图或 SVG 冒充原生页面/数据图 = 直接判不合格**。

## 4. 七种用户裁决语义（穷举，不得自造）

| 裁决 | 语义 | 状态机动作 |
|---|---|---|
| **接受** | 本轮全部条目通过 | 冻结本轮条目 → `round += 1` |
| **部分接受** | 只通过点名条目 | **只冻结被点名条目**；其余条目回退 `pending`，不消耗轮次配额 |
| **返修** | 条目方向对、执行不对 | **仍属当前轮**（`round` 不变）；生成返工单，回灌本轮 |
| **换方向** | 条目层面诊断对但切入点错 | 该条目作废 → 新条目入 `pending`，重新分档 |
| **暂停** | 用户要停，但不终止 | 状态 → `等待用户`，**保留全部现场**，可恢复 |
| **终止** | 用户明示不做 | 状态 → `用户取消`，冻结项与状态文件保留供后续恢复 |
| **沉默/超时** | — | **不构成确认**。状态维持 `等待用户`，绝不自动推进 |

> 硬约束：成员自评、AI 判断、"看起来没问题"均**不构成**用户确认。

## 5. 每轮必须展示的六项（缺任一项 = 本轮无效）

1. **本轮处理范围及问题**——条目 ID + 稳定页面 ID + 原文摘录 + 问题类型 + 严重度 + 判定方式（机/人）
2. **修改前后差异**——逐条对照。**禁止**"整体优化""已优化"这类无定位表述
3. **可阅读的修改后正文**——完整段落，不是摘要
4. **来源定位与边界**——PMID/DOI/指南条目 + 适用边界 + 未决项；无法核验的关键专业结论**不得进入正式内容**
5. **配图建议**——保留 / 替换 / 新增 + 页内位置 + 理由；图像类内容必须**先逐张判读图像本体**（迭代六原则·素材判读红线）：判读不出不得写、低清图降级"情境图"、来源缺失不编造、要素缺项显式挂账
6. **本轮验收结果 + 下一轮候选**——机器项引用**原始计数**（P0/P1/P2/P3），禁"归零/100%"表述（反自评失真红线）

## 6. 冻结粒度与批准失效

冻结对象是**条目级**，条目记录至少含：

```json
{
  "item_id": "R2-D3-007",
  "page_id": "s12",
  "file": "<工作副本>/content/s12_draft.md",
  "sha256": "<该文件内容哈希>",
  "round": 2,
  "user_decision": "accept|partial_accept",
  "decided_at": "<ISO8601>"
}
```

**失效规则（硬约束）**：内容文件 sha256 与冻结记录不一致 → 该条目的批准**自动失效**，必须重审。
禁止"改内容不重审"——这是本 SOP 最容易被绕过的漏洞。

## 7. 五类终止状态

| 状态 | 触发 | 允许动作 |
|---|---|---|
| 成功完成 | 全部条目冻结 + 制作交付 + 独立验收通过 | 交付 |
| 等待用户 | 待裁决 / 待审阅 / 待方向分档 | 停，等用户；**不得推进** |
| 能力或证据阻塞 | 关键能力缺失或关键结论无法核验 | 报缺口 + 核验方法；**不得降级冒充** |
| 达到预算但未完成 | 轮次/检索/无进展阈值触顶 | **暂停并报告，禁止宣布通过** |
| 用户取消 | 用户明示终止 | 停；保留状态文件供恢复 |

参数（`config/harness.yaml#loop_b`，均可调）：
`max_rounds` 轮次上限 · `retrieval_budget_per_round` 每轮检索预算 · `no_progress_threshold` 无进展轮次阈值 · `max_rework_per_item` 单条目返修上限。

## 8. 制作前置门（任一不满足即停）

- 已冻结条目**覆盖**制作输入的全部页面与素材
- 每条冻结项的 `file` sha256 与当前文件一致（不一致 → 批准失效，须重审）
- 内容、页面顺序、配图方案、模板**均已确认**

制作期遇内容问题 → **退回对应内容轮**，不得擅自改写已批准内容。

## 9. 断线恢复

读状态文件最小集：`task_id / source_ppt{sha256,mtime} / wip_dir / current_round / frozen_items[] / pending_items / budgets / blockers`。

禁止：重跑已确认条目、重新生成已冻结内容、覆盖 `_draft`。
恢复后先报"恢复到第 R 轮，已冻结 N 条，待办 M 条"，**等用户确认再继续**。

## 10. 状态文件位置（Loop B 专用）

`<工作区>/.workbuddy/loopB_state.json` —— 与 `task_state.json` **并存，不覆盖**（后者是五道闸的既有状态机，本 SOP 不改其语义）。
写入采用**单写者**（主理人）——成员不得直接写该文件，回传由主理人汇编后落盘。

### 10.1 通道纪律（v3.8.0 增补 N6）

- **只有主理人可向用户提问与接收确认**；成员遇到缺失信息时把问题写进 `issues`，由主理人转达，**不得直接联系用户**
- 成员之间**禁止横向直连**，跨成员信息流一律经主理人中转
- 成员**不得代写**其他成员的专业结论；主理人只做汇编与裁决
- 沉默不等于批准；用户未回应时状态停在 `等待用户`，**不自动推进**

## 11. 终审验收清单（v3.8.0 增补 N5）

交付前逐项打勾，**每项须给出判定依据**，无法检查的写明原因——**不得因"看起来没问题"写通过**：

| # | 验收项 | 判定方式 | 未通过处置 |
|---|---|---|---|
| 1 | 原件未改动 | 原件 sha256/mtime 与任务开始时比对 | 立即停止并上报 |
| 2 | 新建 PPT 能力未回归 | 跑 `ensure_settings` + `test_five_gates.py` | 阻断交付 |
| 3 | 素材链接可解析且可回溯原页 | 逐条解析 `_draft.md` 图片引用 + 反查 `page_id` | 标注缺失项 |
| 4 | 关键专业结论有可核对来源 | `harness.py verify-ref --path <cases_library.json> --online` | 降级或退回内容轮 |
| 5 | 每轮用户批准可追溯 | `loopB_state.frozen_items[]` 含 item_id/file/sha256/decided_at | 不得进入制作 |
| 6 | 配图决策与最终页面一致 | 配图清单 vs 新版页逐条核 | 返修 |
| 7 | PPT 内容与批准稿一致 | 成品文本层 diff `_draft` | 阻断交付 |
| 8 | 模板继承 + 打开 + 渲染 | 打开无异常 + 渲染页数符合 | 报缺口 |
| 9 | 对象可编辑性分级 | §3.3 四类判定 | 截图/SVG 冒充 = 不合格 |
| 10 | 未实现/未测试的检查已标注 | 逐项标 [机]/[人]/lint 未实现 | 不报通过 |

## 12. 与既有规则的优先级

冲突时以本 SOP 为准的两条：
1. 本 SOP 的**逐轮停等**优先于任何"提高效率"的建议——效率不构成跳过的理由。
2. 迭代六原则**全文适用**（本 SOP 不重定义它们，只规定其在逐轮场景下的执行时点）。
