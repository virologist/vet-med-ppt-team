> **背景**：v3.19.3 的 L3 用「段名批量登记」把 75 个死配置键压到 0。
> 批量高效，但**可能掩盖个别键的真实情况**——本轮把当时未逐个性定的

> ⇒ 批量登记**确实埋没了 3 个真缺陷**，逐键定性是必要环节。

## 一、方法与判据

每个键都过三道核查：
1. **读 yaml 原文 + 注释**（理解语义与设计意图）
2. **查代码消费点**（AST 读取集 + 键名字面量 + 真实调用链）
3. **查文档引用**（agents/ + references/ 的 LLM 消费方）

定性三类：
- **A 类（人读型）**：消费方是会话层/成员 LLM/主理人，本就不该由脚本读
- **B 类（漏消费）**：本该被脚本消费却没接 ⇒ **真 bug，接线**
- **C 类（可删）**：确属废弃，无保留价值

## 四、重要澄清：批量登记 vs 逐键定性的关系

**批量登记没有错，但它把 3 个 B 类键和 32 个 A 类键一起压平了**——其中：

- `license_uncertain_markers` 的登记理由原本写「供成员判断许可是否可信，语义判断不由脚本做」
  ⇒ **这个理由不成立**：`fetch_oa_image.py` 正是脚本侧做许可判定的地方，它本该读这个配置。
- `write_gate_level` / `deliver_gate_level` 的登记理由原本写「人读档位说明」
  ⇒ **也不成立**：argparse 的默认值就是脚本消费点，本该从 yaml 读。

⇒ **教训**：批量登记（按段名）后，**必须再用「该键是否有脚本侧职责」反向抽查**。
本轮抽查方式：对每个键问「**如果这个值改了，哪个脚本的行为应该跟着变？**」
答不上来的才是真 A 类；答得上来却没接线的就是 B 类。
